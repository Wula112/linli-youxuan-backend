# JMeter 并发与 Little's Law 复核

复核时间：2026-11-08。对象：2026-11-07 秒杀接口压测中 100 线程、2,000 次请求的 `c100` 阶段，以及相同测试计划的隔离模拟复现。

已按同 JVM 预热脚本的方式完成五档重测，详见[预热重测报告](seckill-load-retest-2026-11-08.md)。

## 结论

100 线程这轮的 37.27 个平均 HTTP 样本在途与 Little's Law 一致。100 是配置的 JMeter 工作线程数，不是整段时间中实际处于 HTTP 采样的平均请求数。本轮 100 个线程的首次请求结束后发生了约 1.16～1.19 秒的请求间隔，其中有 **1.157 秒所有线程都没有 HTTP 样本在途**，而整轮采样窗口仅 1.947 秒。

使用相同的 JMeter 计划和本地固定响应接口复现时，线程栈显示 99 个压测线程阻塞在 JSR223 后置脚本的编译缓存处，另一个线程正在编译 Groovy 脚本。移除该后置处理器，或在**同一个 JMeter JVM** 中先执行相同脚本，均消除了这一秒级首轮间隔。原压测没有保留当时的线程栈，因此不能声称复现栈是原压测的直接快照，但复现与原始 JTL 的时序高度一致，强烈支持该冷启动是主要原因。

此前报告没有识别这一影响；原来给出的短时 QPS 是该次完整窗口的算术结果，**不应解释为 100 个请求持续在途时的稳定吞吐或容量**。

## 100 线程原始数据

JTL 配置确认时间戳为样本开始时间。对 2,000 条 HTTP 采样逐条按 `[timeStamp, timeStamp + elapsed)` 重建：

| 指标 | 结果 |
| --- | ---: |
| 配置线程数 / 每线程样本数 | 100 / 20 |
| 从第一个样本开始到最后一个样本结束 | 1.947 秒 |
| 请求总耗时之和 | 72.561 秒 |
| 平均响应时间 | 36.2805 ms |
| 以同一窗口计算的吞吐 | 2,000 / 1.947 ≈ 1,027.22 次/秒 |
| 平均 HTTP 采样在途数 | 72.561 / 1.947 ≈ 37.27 |

即 `L = λ × W ≈ 1,027.22 × 0.0362805 ≈ 37.27`。这里 `L` 的边界是 **JMeter 记录的 HTTP 样本区间**：它可能包含客户端连接和调度等时间，不应直接当成服务器处理线程数。JMeter 对采样耗时的定义见[官方术语说明](https://jmeter.apache.org/usermanual/glossary.html)。

这轮 JMeter 控制台还输出过约 888.1 次/秒，与报告的 1,027.22 次/秒口径不同：本机 JMeter 5.6.3 的控制台汇总器使用其统计对象的墙钟起止时间，而报告使用 JTL 最早样本开始到最晚样本结束的 1.947 秒。比较吞吐、耗时和平均在途数时必须使用同一时间范围，不能混用两个数字。

同一时间窗口内，把每个线程的相邻请求间隙相加，得到 119.472 线程秒，即平均约 **61.36 个线程处于两次 HTTP 样本之间**。请求采样和相邻样本间隙分别占约 37.27 和 61.36 个线程；剩余约 1.37 个线程对应各线程首末样本之外、JTL 无法覆盖的时间。JTL 并不记录线程在这些边界之外的完整生命周期，不能据此断言这些线程一定未启动或已退出。

100 个线程的首条样本开始时间相差不超过 6 ms。最晚首条样本在窗口开始后 102 ms 结束，最早第二条样本在 1,259 ms 才开始，因此中间有 **1,157 ms 完全没有 HTTP 样本在途**。100 个线程的首次间隔最小 1,157 ms、中位数 1,176 ms、最大 1,191 ms；首次间隔合计占全部相邻请求间隙的约 98.47%。随后请求间隔的中位数为 1 ms。

窗口开始后 1.4～1.8 秒的 400 ms 切片中，按样本重叠时间计算的平均在途数约为 97.13。这是一个很短的事后切片，只能说明线程在冷启动后接近同时发出请求，不能据此声称服务的长期稳定吞吐。

## 独立模拟复现

模拟服务仅绑定 `127.0.0.1:18092`，始终返回固定成功 JSON，不连接业务服务。各轮沿用相同的 JMeter 版本、100 线程、20 次循环、CSV、HTTP 请求和 JVM 参数，每组独立启动 JVM；预热组在同一 JVM 中先由 1 个线程运行一次相同后置脚本，之后再运行 100 线程组。以下只比较各线程首次与第二次 HTTP 样本之间的时间：

| 测试计划 | 两次复测的首间隔中位数 | 两次复测中首间隔超过 500 ms 的线程数 |
| --- | ---: | ---: |
| 原计划：使用 Groovy JSR223 后置处理器 | 1,125 / 1,148 ms | 100 / 100，100 / 100 |
| 移除后置处理器 | 10 / 2 ms | 0 / 100，0 / 100 |
| 保留后置处理器，同 JVM 先预热 | 1 / 1 ms | 0 / 100，0 / 100 |

单独的原计划复现中，在首批请求后采集线程栈：100 个线程处于 `JSR223PostProcessor.process`，其中 99 个在 `JSR223TestElement.getCompiledScript` 的缓存计算处等待同一监视器，1 个线程位于 `GroovyScriptEngineImpl.compile`。这解释了为什么响应时间统计不包含这段等待，但线程无法开始下一次请求。

原测试计划已设置脚本编译缓存，并不是“忘了开启缓存”：缓存中的脚本第一次仍需初始化和编译。每个压测阶段都单独启动一个 JMeter JVM，上一阶段即使执行了脚本，也不会预热下一阶段的进程内缓存。JMeter 的[JSR223 组件文档](https://jmeter.apache.org/usermanual/component_reference.html#JSR223_PostProcessor)说明了可编译脚本的缓存机制。

此模拟实验用于定位压测客户端开销，不能拿模拟服务的吞吐作为秒杀接口性能。无后置处理器的变体只用于隔离原因，并未验证真实业务响应。

## 其他测试阶段

| 阶段 | 统计窗口 | 所有 HTTP 样本均不在途的首轮公共空档 |
| --- | ---: | ---: |
| 10 线程 | 1.926 秒 | 886 ms |
| 50 线程 | 1.592 秒 | 954 ms |
| 100 线程 | 1.947 秒 | 1,157 ms |
| 200 线程 | 2.107 秒 | 1,320 ms |
| 200 线程复测 | 2.460 秒 | 1,672 ms |

因此这些短测的整轮 QPS 均包含显著的客户端冷启动空档；200 线程两轮的连接拒绝仍是实际观察到的结果，不能仅凭此空档确定其原因。请求本身的响应时间分位数仍是记录到的样本统计，但包含首批冷连接等阶段，不能代表持续稳态的分位数。

1,000 线程、5 秒爬升的 20 秒测试中，按相同 JTL 时间窗口计算平均约有 802.09 个 HTTP 样本在途；1,000 个线程中 749 个的首个样本后间隔超过 500 ms，中位数为 1,755.5 ms。该轮还存在爬升与机器资源竞争，不能把所有差额都归因于同一个因素。

之后的单券/多券消费者对照使用同一冷启动计划灌入请求，但数据库建单速率是在灌入结束后另取约 25 秒窗口计算；它仍是该窗口内的观察值，不表示灌入阶段达到了稳定 200 HTTP 并发。

## 建议的重测方式

1. 在同一个 JMeter JVM 中先以独立券和合成用户运行预热线程组，确保与正式线程组执行完全相同的业务响应校验脚本；预热样本单独打标签，并从正式统计中排除。
2. 正式阶段按约定爬升后稳定运行足够长的时间，准备足量独立用户和库存，并分别报告整个阶段及稳定窗口的请求数、HTTP 采样在途数、成功率和 P95/P99。
3. 不因性能原因直接去掉真实压测中的业务结果校验；应继续区分 HTTP 200、成功受理、库存不足和其他业务失败。
4. 尽可能将压测器与服务部署在不同机器，同时记录压测器 CPU、GC、线程、网络及服务端资源；单独观察 MQ 积压、订单落库和最终一致性。
