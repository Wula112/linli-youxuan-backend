# 秒杀接口压测报告

测试时间：2026-11-07，东八区。接口：`POST /voucher-order/seckill/{id}`。

## 主要结果

- 200 个线程同时启动、无爬升的两轮测试中，分别有 95/2,000 和 96/2,000 次请求在建立连接时被拒绝，失败率为 4.75% 和 4.80%。这些请求没有拿到 HTTP 响应；原因尚未定位。
- 200 线程、5 秒爬升的短时测试在 8.941 秒内受理 30,000 个请求，受理吞吐约 3,355 次/秒。测试原计划运行 20 秒，但测试用户数据用尽后提前结束，因此这不是 20 秒持续吞吐，也不能当作稳定容量。
- 上述 30,000 次成功响应代表抢购请求已受理，订单异步创建。最后一个 HTTP 响应结束后，约 6 分 32 秒至 6 分 37 秒之间观察到本批订单全部落库、待处理队列清零。逐笔核对订单 ID 和用户、Redis 与数据库库存，最终均一致。
- 售罄测试中，100 份库存得到 100 笔订单，其余 1,900 次请求返回库存不足；最终未观察到超卖。
- 本次仅在隔离压测实例中关闭了限流切面，正式工作区的秒杀限流代码仍在。限流未关闭时的性能不能根据本报告推算。

压测使用由当前工作树构建的应用副本。该副本通过专用启动初始化器移除了限流切面，并将硬编码为 `127.0.0.1:6379` 的 Redisson 连接改为隔离 Redis；其他业务逻辑与事务切面保留。启动日志确认上述两项生效，测试结束后在隔离 Redis 中未发现 `rate:limit:*` 键。原始应用包和正式源码中的限流逻辑未作改动。

隔离环境的 Redis 未开启持久化，MySQL 未开启 binlog，RocketMQ 为异步刷盘；这些设置不代表生产环境的数据持久性配置，可能抬高测试吞吐。JMeter 与服务共用 CPU、内存和磁盘，不应将结果直接用作独立部署或生产集群的容量结论。测试也没有经过真实登录过程、网关或反向代理。

## 方法与统计口径

- 每个阶段使用独立优惠券和不同的合成用户；请求通过 Redis 中预置的登录令牌认证，HTTP 使用长连接。
- 固定并发阶段为闭环压测，每线程收到响应后立即发送下一次请求，零爬升，每阶段共 2,000 次请求。除售罄测试外，初始库存均为 3,000。
- 下表吞吐按「成功受理数 ÷ 从最早请求开始到最晚请求结束的时间」计算。响应时间只统计业务返回成功的请求，单位为毫秒，分位数使用最近排名法。请求超时设置为连接 5 秒、响应 15 秒。
- 业务成功由响应 JSON 的 `success` 和订单 ID 判定，不能仅凭 HTTP 200 判定。后台落库后，再以订单 ID 和用户 ID 与分片订单表逐笔核对，并检查 Redis、数据库库存和待处理记录。
- 固定并发各阶段仅持续约 1.6～2.5 秒，属于短时突发测试；闭环模式也可能低估拥塞期间的延迟，不能作为长时间稳定性结论。

## 异步建单积压

30,000 请求阶段在 18:07:14.387 返回最后一个 HTTP 响应。随后一次中途核查观察到 15,806 笔订单已落库，仍有 14,194 个成功响应的订单 ID 未查到。之后的采样如下：

| 观察时间 | 数据库订单数 | 待处理数 |
| --- | ---: | ---: |
| 18:09:42.342 | 16,992 | 13,006 |
| 18:13:46.668 | 29,882 | 118 |
| 18:13:51.773 | 30,000 | 0 |

因此，在约 5 秒一次的采样精度下，积压清零发生在最后一次 HTTP 响应后的 392.281～397.386 秒。上述采样时的订单数与待处理数由不同查询读取，存在并发读取误差。采样区间内平均新增约 52 笔订单/秒，只反映该阶段的观察值，不应当作系统长期稳定的建单上限。

测试期间此前阶段的未支付订单达到 15 分钟时限，后台关单和补偿开始运行；2 分钟阈值的对账任务也参与处理积压。它们与消费者共享 MySQL、Redis 等资源，应用还开启了 SQL DEBUG 日志。观察期间熔断状态未见开启。测试无法单独确定积压由哪一处导致，也未验证死信、故障恢复或订单详情页触发建单。

### 对积压原因的日志补充分析

建单消费线程固定为 4 个。RocketMQ 客户端对两个约 1 分钟时间段的统计显示：

| 日志统计时刻 | 成功消费吞吐 | 单次消费平均耗时 |
| --- | ---: | ---: |
| 18:08:59 | 110.66 次/秒 | 36.14 ms |
| 18:11:59 | 43.80 次/秒 | 91.39 ms |

例如，在第一个区间，`110.66 × 0.03614 ≈ 4`，表明平均约 4 个消费线程同时处于消息处理过程，消费线程已基本忙满。随着单次处理耗时上升，吞吐从约 111 次/秒降至约 44 次/秒；这说明消费能力跟不上受理速度，但不能单凭此断言增加线程就能解决问题。

本轮 3 万次请求针对同一张券，所有新订单的数据库事务都要更新同一条库存行。建单事务在库存更新后还会写入订单、路由和处理状态，并使用 XA 事务；提交前，其他修改同一库存行的事务可能等待。相近时间的 MyBatis 日志中，该券库存更新从打印参数到返回结果的耗时，18:08 的 6,653 次平均为 15.52 ms、P95 为 30 ms；18:11 的 2,834 次平均为 37.23 ms、P95 为 74 ms。该耗时还包含 SQL 执行、框架和系统调度，**不能等同于纯行锁等待**，也不能据此计算行锁造成的损失比例。

提交后，消费线程还需要清理 Redis 待处理记录并同步发送延迟关单消息；关单、对账、XA、DEBUG 日志和同机压测也可能影响处理耗时。订单处理记录按订单 ID 区分，不同订单通常不会竞争同一条处理记录；对账和消费者同时处理同一订单时则会竞争。

要区分线程数和库存行竞争的影响，建议在隔离环境中固定线程数分别测试单券和多券，并选择路由到同一物理库表、但库存行不同的券；同时逐级比较 1、4、8、16 个消费线程。每轮采集 RocketMQ 的消费速率、处理耗时和队列积压，以及 MySQL `performance_schema.data_lock_waits`、行锁等待增量与事务耗时。增加线程后若吞吐提升很小而锁等待上升，说明热点行竞争更突出；如果锁等待不明显且吞吐持续提升，线程并发不足的影响更大。

## 建议

1. 对用户展示时区分「请求已受理」与「订单已创建」，持续监控从受理到订单可查询的耗时、待处理数量和最老请求年龄；在当前熔断条件之外评估基于积压的保护策略。此次 30,000 笔最终一致，但正常运行压测不能证明故障场景下一定建单成功。
2. 使用独立压测机复现 200 线程突发连接拒绝，采集操作系统和 Tomcat 的连接、监听与等待队列指标，并对比不同爬升时间；定位后再决定是否调整连接队列配置。
3. 分别观测 RocketMQ 消费延迟、对账任务、数据库事务与热点库存行锁等待、磁盘和日志开销。增加消费者线程前先确认热点行和数据库是否有余量。
4. 在接近生产的持久化、日志、分库和网络配置下开展更长时间的阶梯及稳定负载测试，并单独验证重试耗尽、死信告警、熔断、订单查询补建与超时关单回补。
5. 建议将 Redisson 地址改为使用统一配置，避免运行环境调整 Redis 端口时误连默认的 `127.0.0.1:6379`。
