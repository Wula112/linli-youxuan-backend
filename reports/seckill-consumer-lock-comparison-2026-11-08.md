# 秒杀建单消费者与库存行锁对照报告

测试时间：2026-11-08 12:11～12:22，东八区。目的是区分增加消费线程和分散库存行对积压处理的影响。

## 结论

- 单券场景从 4 个线程增加到 8、16 个线程，25 秒窗口内入库速度分别约为 **137.11、140.97、133.46 笔/秒**，没有随线程数明显提升。MySQL 全局行锁等待平均值分别约为 **11.20、39.26、58.18 ms/次**。
- 使用相同消费线程数时，8 券场景的入库速度比单券分别高约 **29.1%、33.4%、36.8%**。单券各组的 24 次采样均观察到目标库存表主键记录的锁等待；8 券各组分别有 1、2、16 次观察到。
- 结果强烈支持：**同一券的数据库库存行是当前测试条件下的重要瓶颈之一，不能靠简单增加消费线程消除。** 多券从 4 增至 16 线程的收益也很有限，说明还需要继续分析整个建单链路，不能把全部耗时归因于库存行锁。

| 观察窗口 | 最后一次 HTTP 响应后约 1.8～2.2 秒开始，固定观察约 25 秒；窗口结束时各组仍有约 1 万笔以上待处理预占 |

按此前要求，本次每组只采集固定窗口，不等待消息全部处理。每组结束后关闭隔离服务。Redis 未开启持久化、MySQL 未开启 binlog、RocketMQ 异步刷盘；应用保留 SQL DEBUG 日志，这些条件均可能影响吞吐。

**压测客户端口径补充：**各组灌入请求时分别启动新 JMeter 进程，后置 Groovy 脚本存在首次初始化；6 组分别有 38～43 个请求线程的首个样本后间隔超过 500 ms，因此灌入阶段不代表持续稳定的 200 HTTP 并发。下表测量的是灌入结束、JMeter 已退出后约 25 秒的数据库建单增量，各组在窗口结束时均仍有积压。详见[JMeter 复核报告](jmeter-littles-law-diagnosis-2026-11-08.md)。

| ---: | ---: | ---: | ---: |
| 4 | 3,441 / 137.11 | 4,450 / 177.04 | +29.1% |
| 8 | 3,538 / 140.97 | 4,720 / 188.04 | +33.4% |
| 16 | 3,354 / 133.46 | 4,582 / 182.55 | +36.8% |

入库速度以同一测试券集合的数据库已提交订单数在观察窗口内的增量，除以两次数据库读取中点的时间差计算；不是 HTTP 接口受理速度，也不是精确的 RocketMQ ACK 速率。25 秒观察结束时，6 组 Redis 待处理数分别仍为 11,843、11,777、11,963、10,578、10,033、10,221；各组检查到的熔断标记均未开启。

## 行锁与库存 SQL

| 消费线程 | 单券：行锁等待次数 / 均值 | 8 券：行锁等待次数 / 均值 | 单券：命中库存行等待的采样 | 8 券：命中库存行等待的采样 |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 3,442 / 11.20 ms | 220 / 4.35 ms | 24 / 24 | 1 / 24 |
| 8 | 3,538 / 39.26 ms | 712 / 8.18 ms | 24 / 24 | 2 / 24 |
| 16 | 3,353 / 58.18 ms | 1,558 / 16.29 ms | 24 / 24 | 16 / 24 |

等待次数和均值由窗口首尾的 MySQL 全局状态 `Innodb_row_lock_waits`、`Innodb_row_lock_time` 差分计算，覆盖该实例的所有 InnoDB 行锁，不能单独视为库存行的精确耗时。采样列约每秒查询一次 `performance_schema.data_lock_waits`，并确认等待对象为 `hmdp_0.tb_seckill_voucher_0` 的主键记录；采样反映时刻命中情况，不是完整事件计数。`data_lock_waits` 中一笔等待可能对应多条阻塞关系，不应把关系条数当作等待线程数。

同一窗口内，从 MyBatis 打印库存更新参数到打印更新结果的时间如下：

| 消费线程 | 单券：平均 / P95 | 8 券：平均 / P95 |
| ---: | ---: | ---: |
| 4 | 12.09 / 16 ms | 1.20 / 2 ms |
| 8 | 40.12 / 47 ms | 3.05 / 12 ms |
| 16 | 67.84 / 102 ms | 11.33 / 35 ms |

该时间包含 SQL 执行、框架调用和系统调度，不能直接当作纯行锁等待或完整事务耗时。应用日志中分别观察到了对应的 4、8、16 个消费线程；本轮日志未发现订单消费失败、死锁或锁等待超时。

## 解读与后续排查

同一张券的订单事务都会更新同一个库存主键行；锁持有到事务提交或回滚。把请求分散到同库同表的不同库存行后，等待显著减少、建单吞吐上升，因此热点库存行对本轮积压有实质影响。处理记录按订单 ID 区分，本轮不同订单通常不会竞争同一条处理记录。

4 线程单券已接近本次测试中的热点行处理能力；增加到 16 线程主要增加等待，暂不建议仅通过提高线程数治理单券积压。8 券场景下增加线程仍未带来接近线性的提升，下一步应分别测量库存行锁持有到 XA 提交的时间、数据源连接池等待、提交后的 Redis 清理与延迟消息发送、磁盘以及 DEBUG 日志开销，再决定优化点。任何事务路径或库存模型调整都需要维持现有建单、关单和补偿的幂等与一致性。

每种组合只测了一轮、窗口约 25 秒，且所有进程共用一台机器；结论适合定位方向，不能代表长期或生产环境容量。Redis 待处理数量不等同于 Broker 的精确积压量。本次未等待队列清空，也没有验证每个成功请求最终建单或最终库存一致性。
