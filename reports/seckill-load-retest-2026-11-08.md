## Little's Law 核对

| JMeter 线程 | 时间加权平均在途 `L` | 窗口完成吞吐 × 平均耗时 `λW` |
| ---: | ---: | ---: |
| 10 | 9.734 | 9.734 |
| 50 | 49.618 | 49.619 |
| 100 | 99.616 | 99.620 |
| 200 | 198.548 | 198.551 |
| 1,000 | 999.582 | 999.806 |

例如 100 线程档：`4,018.80 × 0.024789 ≈ 99.62`，与按样本起止时间直接计算的 99.616 基本一致。`L` 的边界是 JMeter HTTP 采样，不等同于服务端同时处理的线程数。`λW` 使用窗口内完成的请求的完整耗时，而 `L` 将跨越窗口边界的样本裁切后计入；边界差异和毫秒时间戳精度会造成小幅误差。

五档的正式组首个请求后间隔中位数均为 1 ms，均没有出现超过 500 ms 的首次间隔；同一 JVM 内预热消除了前次复现的秒级首次编译停顿。

## 请求结束后的快照

每档在最后一条 HTTP 响应后约 1.75～2.08 秒开始读取一次 Redis 和数据库。快照覆盖该档完整约 75 秒正式阶段，因此受理数大于上表 60 秒窗口数；Redis 和数据库不是同一原子快照。

| ---: | ---: | ---: | ---: |
| 10 | 198,951 / 401,049 | 8,050 | 190,912 |
| 50 | 326,832 / 273,168 | 8,719 | 318,123 |
| 100 | 295,561 / 304,439 | 8,325 | 287,247 |
| 200 | 276,963 / 323,037 | 7,341 | 269,633 |
| 1,000 | 290,877 / 309,123 | 8,450 | 282,437 |

每档初始库存均为 600,000，快照时 Redis 熔断标记均未开启。Redis 待处理记录不等同于 RocketMQ Broker 精确积压量；快照后按要求关闭隔离服务，没有等待消息全部消费，也没有验证所有订单最终创建和最终库存一致性。

## 配置与限制

- 五档各使用全新隔离 MySQL、Redis、RocketMQ 数据目录和单个应用实例；应用、依赖与 JMeter 同在一台 Windows 11、16 核 32 线程的主机上。
- JDK 21.0.10、JMeter 5.6.3、MySQL 8.4.8、Redis 8.10.2、RocketMQ 5.5.1；应用使用分片和 XA，两个逻辑数据源位于同一 MySQL 实例，订单消费线程数为 4。
- 每档准备 600,000 个合成用户和足量库存，正式请求使用的用户均不重复。先用独立券验证 MQ 消费就绪；随后在**同一 JMeter JVM** 用另一张券执行 200 次相同业务校验脚本，再运行正式组，预热样本不计入表格。
- 限流只在隔离压测副本中关闭，业务源码保持现状；本地调度器开启。测试 Redis 未持久化、MySQL 未启用 binlog、RocketMQ 异步刷盘；这些条件与生产耐久性配置不同。
- 每档只运行一次，共机资源竞争、不同的短期负载变化和客户端毫秒时间戳精度都会影响结果。表中数值不能直接作为生产环境长期容量或订单落库吞吐。
