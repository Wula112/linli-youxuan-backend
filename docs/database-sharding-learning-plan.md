# hmdp 分库分表设计：完整学习版

> 历史设计：2026-10-27 已按最新约定落地精简的 XA 方案，当前实现与启动步骤见 [两库两表与 XA 实现](database-sharding.md)。下文包含的 Outbox、额外对账/补偿表和其他业务域分片不属于当前实现。

日期：2026-10-18。目标：在现有邻里优选项目中完整学习分片路由、多维查询、跨库事务、异步一致性、迁移与故障恢复。本文取代 `database-sharding-plan.md` 的最小改动推荐；既有数据量只作为调研记录，不决定学习范围。

本方案是设计文档，尚未修改数据库、引入中间件或执行迁移。

## 1. 对两份参考脚本的重新评价

两库两表、手机号目录、订单路由目录、对账与补偿的方向可以保留，适合作为学习主线。订单与库存跨库是一个需要解决和验证的设计问题，可以选择 XA，也可以选择有明确状态机的最终一致性。

仍需修正的具体缺陷：库存缺少券 ID 唯一索引，订单缺少业务唯一约束，订单目录缺少订单号唯一索引，用户详情缺少用户 ID 唯一索引，手机号目录缺少唯一约束；订单状态字段存在 `int/tinyint` 分片差异；重复的笔记、店铺等表没有配套配置就无法判断其角色。

评价标准是：每个核心接口如何定位数据、业务约束如何保证、哪个事务承担哪些写入、失败后由谁恢复，以及如何通过实验验证。

## 2. 拓扑与统一路由约定

```text
Spring Boot / MyBatis-Plus
            |
   ShardingSphere 逻辑数据源
            |
       +----+----+
       |         |
      ds_0      ds_1
    hmdp_0    hmdp_1
```

开发阶段可用同一 MySQL 实例中的两个 schema 验证路由；事务故障和资源隔离实验再使用两个独立实例。两个 schema 不意味着拥有两台机器的吞吐或容灾能力。

数值型、正整数 ID 的基础函数：

```text
D(k) = k % 2                    # 数据库编号
T(k) = floor(k / 2) % 2          # 表后缀
R(k) = (D(k), T(k))

100 -> ds_0.table_0
101 -> ds_1.table_0
102 -> ds_0.table_1
103 -> ds_1.table_1
```

保留 `intdiv(2)` 的目的，是让库号和表后缀分别利用不同位置的信息，覆盖 4 个位置。所有 ID 使用一致的 BIGINT/Java Long 语义；不要在不同入口混用字符串哈希、Long 哈希和整数取模。

手机号是字符串，应先规范化再路由。为避免语言和类型带来的哈希差异，学习版可固定：规范化号码的 UTF-8 字节 → SHA-256 → 取前 8 字节按无符号大端整数解释 → 取模 4 得到槽号 s；库号为 `s % 2`、表后缀为 `s / 2` 的整数部分。实现时使用能正确处理无符号值的算法，不用浮点数。

这些是初始拓扑规则，不是无迁移扩容算法；也不保证任意 ID 生成器下数据天然均匀。需要用生成器的真实输出测试单节点、并发多节点及低并发情况下的分布。

## 3. 业务表与路由目录

| 逻辑表 | 推荐位置/路由 | 核心约束与用途 |
|---|---|---|
| `tb_user` | `R(id)` | `PRIMARY KEY(id)`；按用户 ID 精确查询 |
| `tb_user_info` | `R(user_id)` | `PRIMARY KEY(user_id)` 或 `UNIQUE(user_id)`；与用户同路由 |
| `tb_user_phone` | 规范化手机号的固定哈希路由 | `UNIQUE(phone)`，保存 `phone → user_id`，作为登录目录与手机号唯一性事实来源 |
| `tb_voucher` | `R(id)` | `PRIMARY KEY(id)`；`INDEX(shop_id,status)` |
| `tb_seckill_voucher` | `R(voucher_id)` | `PRIMARY KEY(voucher_id)`，或保留独立 ID 并增加 `UNIQUE(voucher_id)` |
| `tb_voucher_order` | 库 `D(user_id)`；表 `voucher_id % 2` | 保留参考方案的混合键实验；`PRIMARY KEY(id)`、`UNIQUE(user_id,voucher_id)` |
| `tb_voucher_order_router` | `R(order_id)` | `PRIMARY KEY(order_id)` 或 `UNIQUE(order_id)`，保存用户 ID 与券 ID |
| `tb_voucher_reconcile_log` | `R(order_id)` | 独立日志 ID；`INDEX(order_id,create_time,id)`，允许一个订单多条审计日志 |
| `tb_shop` | 明确固定在 `ds_0` 的单表 | 保留分类索引、Redis GEO、详情缓存，作为单表规则的学习对象 |
| `tb_shop_type` | 两库广播表 | 低频变更字典；所有写入经过统一入口并验证副本一致 |
| `tb_blog` | `R(id)` | 详情、点赞和 Feed ID 回表可精确路由；作者列表走下述读模型 |
| `tb_blog_comments` | `R(blog_id)` | `INDEX(blog_id,parent_id,create_time,id)`；评论与所属笔记同路由，接口携带 blog_id |
| `tb_follow` | `R(user_id)` | `UNIQUE(user_id,follow_user_id)`；负责关注方向 |
| `tb_sign` | `R(user_id)` | 需要持久化签到时使用 `UNIQUE(user_id,date)`；Bitmap 作查询加速 |
| `tb_rollback_failure_log` | 固定在 `ds_0` 的单表 | 记录诊断信息；不将一张日志表直接当作可靠重试队列 |

用户主表中的局部 `UNIQUE(phone)` 可以作为额外防线，但跨分片手机号唯一性由按手机号路由的目录保证。手机号字段应符合当前号码模型；参考脚本的 `VARCHAR(512)` 与用户主表的 `VARCHAR(11)` 应统一设计。若仅支持当前 11 位号码可统一为 11；支持国际号码时先定义包含国家码的规范格式。

订单唯一键沿用当前“一人一券一单”的语义。如果允许取消后重买，或一个券对应多个活动批次，先增加活动/购买资格模型，再定义唯一约束。

可以把用户/用户详情、券/库存、笔记/评论设计成同路由表组，但必须在配置和 SQL 中显式满足绑定表条件；相同后缀不自动构成绑定表。依据：[ShardingSphere 表与分片概念](https://shardingsphere.apache.org/document/current/en/features/sharding/concept/)。

## 4. 查询成本与读模型

### 4.1 订单保留混合键的理由和代价

保留参考方案的 `数据库按用户、表按券`，可以学习两个维度各自缩小部分路由范围，而不是宣称两个维度都能单表查询。

| 条件 | 精确路由范围 |
|---|---|
| 用户 ID + 券 ID | 1 库 1 表 |
| 仅用户 ID | 1 库 2 表 |
| 仅券 ID | 2 库各 1 表 |
| 仅订单号，直接访问订单主表 | 2 库 4 表 |
| 仅订单号，先查目录 | 1 个目录分片，再查 1 个订单分片 |

个人订单列表使用 `(user_id,create_time DESC,id DESC)` 索引。在两个目标分片中应用同一游标，各取最多 pageSize 条后按 `(create_time,id)` 归并出 pageSize 条。是否由中间件完成归并，需要针对选定版本验证实际 SQL 与分页结果。不要每次翻页读取全量历史数据，也不要依赖无序分页。

如果压测或接口权重表明个人订单列表更重要，可以做对照版本：订单库、表都采用 `R(user_id)`，个人列表降为一张表，而仅按券查订单扩大为四张表。比较实测查询代价后选择，不把它当作绝对优劣。

### 4.2 多维查询的具体处理

| 查询 | 主路径 | 需要新增的结构或约定 |
|---|---|---|
| 手机号登录 | phone → 手机号目录 → user_id → 用户/详情 | 用户注册在第一版中用 XA 保证用户、详情、目录共同提交；手机号更换同样维护目录 |
| 订单详情/第三方回调 | order_id → 订单目录 → user_id/voucher_id → 订单 | 目录持久化且唯一；缓存只加速，不能作为唯一路由来源 |
| 店铺上架券列表 | 第一版在 4 个券分片上按 shop_id/status 过滤 | 使用同路由券/库存关联；增加分片内索引。优化实验再建立按 shop_id 路由的 `tb_shop_voucher_index` |
| 作者笔记列表 | 按 user_id 查 `tb_user_blog_index` → 批量按 blog_id 回表 | 索引表按 `R(user_id)`，唯一 `(user_id,blog_id)`，排序 `(user_id,create_time,id)` |
| 热门笔记 | Redis 排行取 ID → 按笔记路由批量回表 | 排行是可重建读模型；点赞变更事件更新，明确允许的延迟 |
| 关注动态 | Redis Feed 获取 blog_id → 分组回表 | 合并结果后恢复 Feed 原始顺序；不要假设跨分片 `ORDER BY FIELD` 自动保持全局顺序 |
| 查我的关注 | `tb_follow` 按 user_id 路由 | 正向唯一键 |
| 查某作者粉丝 | `tb_follower` 按 follow_user_id 路由 | 反向关系唯一 `(follow_user_id,user_id)`，带版本/删除状态防止旧事件复活关系 |
| 评论与回复 | 按 blog_id 路由 | 回复请求保留 blog_id，并验证 parent/answer 属于该笔记 |
| 对账与重试扫描 | 调度器枚举已登记的物理分片 | 分片内按状态/到期时间游标扫描，避免在线请求触发无界全库扫描 |

读模型不是另一个可随意修改的事实来源。笔记事实来自 `tb_blog`，关注事实来自 `tb_follow`。第一版可用 XA 同步写事实表与目录/反向关系；异步演进版通过 Outbox 投递变更，以实体版本实现去重和乱序处理，并支持从事实表重建。

基础查询中的 JOIN 不跨任意业务域拼接：例如订单展示的用户昵称、券标题可以通过服务层批量获取。若订单需要永久保留购买当时的标题、金额，应在订单中保存明确的交易快照，而不是依赖后来可变的券信息。

## 5. 第一版：数据库内采用 XA，数据库外采用可靠事件

第一版明确选择 XA 来完成数据库内跨库原子提交。这里有实际的学习内容：事务上下文、参与者、提交/回滚、恢复日志、进程故障与未决事务。

```text
XA 事务内：
  订单分片：创建订单 + 业务唯一约束
  库存分片：stock > 0 条件扣减
  路由分片：写订单目录
  请求分片：更新受理结果
  事件所属库：写 Outbox

事务提交后：
  Outbox 发布消息
  更新 Redis 的预留状态、查询缓存与读模型
```

ShardingSphere 的 LOCAL 事务不能代替跨节点事务。XA 也需要实际接入合适的事务管理器、XA 资源与持久恢复配置；仅添加普通 `@Transactional` 或修改一个配置字符串不足以证明已经正确接入。当前 Spring Boot 4.1.1、JDK 21、MyBatis-Plus 3.5.17 的依赖组合需通过兼容性实验确认，本文不声称已经验证。参见 [官方事务说明](https://shardingsphere.apache.org/document/current/en/features/transaction/)和[事务 API](https://shardingsphere.apache.org/document/current/en/user-manual/shardingsphere-jdbc/special-api/transaction/)。

XA 只覆盖已加入事务的数据库资源。Redis、HTTP 和普通消息发送不因数据库回滚而自动撤销。Outbox 的作用是将业务变化与待发布事件写入同一数据库事务，发布器随后重试发送；发送成功但尚未标记已发送时进程崩溃，仍可能重复投递，因此消费者必须幂等。依据：[Debezium Outbox 文档](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)。

### 5.1 为异步受理保留可恢复事实

建议增加 `tb_order_request`，按 `R(order_id)` 路由，包含订单号、用户、券、请求状态、版本、创建/更新时间以及必要的失败原因。它负责受理过程；订单目录负责长期定位；订单表负责已形成的业务订单，三者职责明确。

```text
INIT → READY → PROCESSING → SUCCEEDED
                    └────→ REJECTED
```

流程：

1. 服务端生成订单号，先持久化 INIT 请求。以订单号或明确的客户端幂等请求标识识别重试。
2. Lua 按该订单号做幂等 Redis 库存预留；同一预留重复执行不能再次扣减。用户/券已由其他订单预留时返回可识别的既有请求，不盲目生成新成功订单。
3. 预留成功后，在请求所属库的本地事务中更新 READY 并写 `CreateOrder` Outbox 事件，随后向客户端返回已受理。本设计将消息发布统一交给 Outbox，Lua 负责预留。
4. INIT 超时扫描恢复进程中断：使用同一订单号检查/重试幂等预留，或进入取消处理。恢复者和正常请求必须通过版本、租约和条件状态变更协调，不能同时执行相互矛盾的动作。
5. 消费 CreateOrder，用 XA 完成订单、库存、目录、请求结果与后续事件写入。重复投递先辨识请求/订单结果，唯一冲突不得造成再次扣库存。
6. 对明确回滚的业务失败，持久化 REJECTED 与库存预留释放任务；释放按预留 ID 幂等执行。对 XA 提交结果未决的事务，先等待事务恢复确认结果，不能按超时直接释放库存。
7. 客户端按订单号查询受理结果；成功后通过目录读取订单。接受请求不等于订单成功。

这条路径为了得到可恢复的受理事实，增加了数据库写入与状态管理成本，是可靠性学习方案，不预设其吞吐高于现有 Redis Lua + Stream 路径。可用故障实验和压测比较两种入口设计。

当前 Lua 仅有用户集合，尚不具备上述按预留 ID 的完整幂等/终态协议；现有消费代码也未实现这个状态机。不能只建表而宣称该流程已具备。

### 5.2 支撑表的最小约束

| 表 | 分布 | 必要约束/索引 |
|---|---|---|
| `tb_order_request` | `R(order_id)` | `PRIMARY KEY(order_id)`；`INDEX(state,update_time,order_id)`；version/执行租约 |
| `tb_outbox_event` | 每个物理库各一张，同业务事实明确路由 | 全局事件 ID；状态、next_retry_at、重试次数；`INDEX(status,next_retry_at,event_id)` |
| `tb_inbox_event` | 消费效果所属物理库，明确路由 | `UNIQUE(handler,event_id)`；去重记录与数据库效果处于同一事务 |
| `tb_compensation_task` | `R(order_id)` | `UNIQUE(order_id,action)` 或经业务确认的补偿幂等键；状态/下次重试时间索引 |

Outbox/Inbox 的“每库一张”是与事实数据同库的本地基础设施，需要显式选库，不能当成任意选库的广播表。不能先把 Inbox 提交为已处理，再单独执行可能失败的业务写入。

数据库事实已提交之后才能确认成功消息。永久失败写入可恢复的失败/补偿记录后结束消费；临时失败重试。审计日志可以有多条，执行幂等标识需要稳定且唯一，两者不混用。

## 6. 第二版：用业务状态机替换 XA，学习最终一致性

第二版是独立演进实验，替换第一版跨库订单事务，不能一边假定 XA 原子性，一边仅靠异步消息执行其中某个参与者。

```text
请求/订单域本地事务：
  待确认订单 + RequestInventory 事件

库存域本地事务：
  幂等库存预留账本 + 条件减可用库存 + 处理结果事件

订单域本地事务：
  根据结果推进订单状态 + 确认/取消事件

库存域本地事务：
  根据确认/取消推进预留终态；取消时仅释放一次
```

库存预留账本按 `R(voucher_id)` 与库存同路由，使用 `UNIQUE(voucher_id,order_id)`；状态至少区分 RESERVED、CONFIRMED、CANCELLED。重放相同请求返回既有结果，不重复修改库存。

需要明确解决：取消先于预留到达时保存取消标记；迟到的预留不得覆盖取消终态；取消与确认竞争使用条件状态更新；没有最终确认前不对外展示成功。业务退单发生在确认之后时，使用独立、幂等的退款/释放事件，而不是把已取消请求重新激活。

目录与读模型在这个版本允许受控延迟：未生成目录时通过持久请求返回“处理中”，不能把“索引尚未更新”解释成订单不存在。状态变化事件携带实体版本，拒绝旧版本覆盖新状态。

对账依据是数据库订单、库存账本和补偿任务。Redis 是预留/查询加速状态；对账不能仅比较两个瞬时库存数。在无补货/退货的实验活动中，应验证初始额度 = 可用额度 + 有效预留额度 + 已确认消耗额度；有补货、取消、退单时分别纳入事件账本。

先完成第一版的跨库事务与故障恢复，再引入该版本，便于比较一致性、延迟、锁等待及维护成本。

## 7. 必须覆盖的实验

| 实验 | 验收标准 |
|---|---|
| 4 个物理位置的路由 | 输入键、SQL 条件与实际库表对应；带两个订单键只访问一张表 |
| 缺少分片键 | 用户列表 2 表、券列表 2 库的范围符合预期；线上写操作不会无意全路由 |
| 同一用户并发抢同一券 | 业务唯一约束生效，只产生一个有效购买资格，不重复扣库存 |
| 只有订单号/手机号 | 目录查询命中唯一索引，准确到达事实表；目录与事实不一致可以恢复 |
| XA 库存更新后订单写失败 | 所有数据库参与者回滚；未决事务经过恢复后有确定结论 |
| Outbox 发送后进程崩溃 | 允许重发，消费效果只有一次 |
| Redis 预留后进程崩溃 | INIT 请求可发现并恢复，既不永久占库存，也不重复释放 |
| 取消、确认、消息乱序 | 条件状态机保持终态，不出现取消后被迟到请求复活 |
| 热门券 | 观察到库存仍集中在单行；订单分片不被误认为库存热点已消失 |
| 读模型延迟/损坏 | 接口行为有明确约定；作者目录、粉丝索引、排行榜可重建 |
| 分片结构差异 | 自动比较字段、索引和约束，所有同逻辑分片一致 |
| 多节点 ID 与分布 | 主键不冲突；验证 ID 类型、序列位与初始路由的负载分布 |

## 8. 迁移、扩容与实施顺序

迁移前先固定规则版本和唯一约束，清理两库中无明确角色的重复数据。参考脚本中的笔记不能既作为两份完整复制，又作为互不重叠的水平分片；按本方案应依笔记 ID 重新分布。店铺固定在 ds_0；类型字典统一广播。

教学初次迁移采用维护窗口：停业务写入口，处理完已受理请求、消息和补偿，再暂停消费者；按规则导入；核对总行数、逐行内容、路由位置、目录对应关系和业务唯一性；切换所有应用到同一配置。产生新写入后回滚必须合并新数据，不能仅切回旧配置。

两库扩为四库时，不直接更改取模数。扩容实验可引入固定逻辑桶和版本化映射：键先定位逻辑桶，再定位实际节点；搬迁仍需要停写/增量同步/校验/切换协议。目录建议保存业务路由键，避免把可变的物理库名写死。

建议实施顺序：

1. 统一 DDL、全局 ID、数值类型和约束，建立 2 库 × 2 表及路由验证。
2. 完成用户/手机号目录、券/库存、订单/订单目录的读写与查询矩阵。
3. 接入并验证 XA，确认注册和下单的跨库事务、异常回滚与恢复。
4. 完成持久请求、Outbox/Inbox、幂等预留、补偿任务与对账。
5. 加入笔记、作者目录、关注双向关系与广播/单表规则，验证多维查询。
6. 做独立的最终一致性版本，与 XA 版本进行相同故障场景和负载对比。
7. 最后进行扩容迁移、读写分离和库存热点处理实验；读副本不能默认承担交易刚写后的强一致查询。

学习版保留了完整的技术问题，但每一阶段都有可检查的结果。当前交付仅更新设计；上述 DDL、框架、状态机和测试尚待实现。
